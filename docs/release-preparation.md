Runtime bootstrap в `lib/db/client.ts` создаёт часть таблиц/колонок, но не заменяет явную проверенную миграцию. Не импортировать его на действующей базе и не обходить это через `drizzle-kit push`.

**Получен SCHEMA_READ_OK; следующий исторический блок повторять не нужно.** Точная старая схема с типами, defaults, ограничениями и индексами получена от владельца и сохранена без пользовательских данных в tests/fixtures/production-schema-20261029.json. Краткий inventory содержит только имена/типы колонок; вывод владельца включал только имена/число строк таблиц. Следующий блок читает **уже созданный backup**, не production. Он выводит определения схемы и количество нарушений FK по связям, без пользовательских строк, email, хешей паролей или содержимого платежей. Запускать на **VPS под root**:

## DNS основного домена — отдельная задача восстановления

Владелец получил от `.ru`: `blablablarden.ru NS ns1.hosting.reg.ru / ns2.hosting.reg.ru`, TTL 345600. Это подтверждает делегацию на DNS веб-хостинга, но не наличие или отсутствие A-записи. Сбой зоны `blablablarden.ru` не является DNS-причиной сбоя другого имени `winds-jesus-boards-application.trycloudflare.com`.

Для VPS у REG.RU есть независимые от веб-хостинга DNS `ns1.reg.ru` / `ns2.reg.ru`; зона управляется в карточке домена. Целевая A-запись корня `@` — подтверждённый публичный IP VPS `80.78.248.233` (www при использовании — тот же адрес или CNAME на корень). Это план, не применённое изменение. Перед сменой NS сохранить/перенести существующие MX/TXT/поддомены, проверить DNSSEC и уже начатые владельцем изменения; не удалять неизвестные записи и не привязывать публичное имя к приватному адресу 192.168.0.199. Если DNS уже восстанавливают отдельно, не дублировать изменения. Официальные инструкции: [привязка домена к серверу](https://help.reg.ru/support/dns-servery-i-nastroyka-zony/rabota-s-dns-serverami/kak-privyazat-domen-k-ip-adresu), [DNS веб-хостинга](https://help.reg.ru/support/dns-servery-i-nastroyka-zony/nastroyka-resursnykh-zapisey-dns/nastroyka-resursnykh-zapisey-na-hostinge). DNS/SSL для публичного переключения ещё требуют проверки; подготовительную копию и репетицию можно делать раньше.

Число реальных пользователей нужно получить из целевой базы, а не принимать за контрольную константу.

Старый `release.sh` делал `db:push || true`, запускал изменение связей произведений, переписывал nginx и завершал все Next-процессы. Эти действия удалены из автоматического пути. `npm run deploy` теперь останавливается с инструкцией; исполняется только явно выбранная offline-проверка. До согласованного выпуска автоматическое переключение не подготовлено.

## Проверяемая репетиция

1. Получить разрешённый read-only inventory production: schema, migration ledger/checksums, SQLite/Node версии, реальные пути, counts пользователей/пометок/подписок/платежей, список файлов. Подготовлен `scripts/inspect-production.cjs`; он не импортирует приложение. Не запускать приложение новой версии ради этой проверки: `lib/db/client.ts` содержит старые runtime DDL.
2. Создать консистентную копию через SQLite backup API (существующий `scripts/backup-sqlite.cjs`), включая подтверждение восстановления. Обычное копирование одного `.db` при активном WAL не подходит. Для согласованности БД и файлов нужен согласованный период остановки записи либо snapshot файловой системы; все источники записи должны быть учтены.
3. Перенести копию и каталоги файлов в закрытую offline-среду. Не переносить боевые платёжные ключи. Внешние cron/webhook/autopay выключены на уровне окружения. Копия должна быть самодостаточна: файловые симлинки наружу проверка отклоняет.
4. Запустить из проверенного checkout:

   ```bash
   bash deploy/release.sh --check /offline/source.db /offline/reports /offline/copied-app --bootstrap
   ```

   Скрипт открывает source read-only, создаёт новый каталог с правами 700, делает backup → restore. Применяет только явные миграции к restored. Сравнивает хеши **всех исходных строк по исходным колонкам**, проверяет прежние ledger-записи, повтор миграций, integrity, набор прежних FK-нарушений и SHA-256 всех связанных файлов. Новые FK-нарушения/изменения данных/отсутствующие файлы/неизвестная схема — неуспех с приватным отчётом. Исторические FK-нарушения перечисляются отдельно; автоматически не исправляются.
5. Если миграция отсутствует в ledger, но её колонка уже существует, **остановиться**. Не помечать её выполненной и не подавлять ошибку. Нужна отдельная аддитивная процедура согласования фактической схемы. Не редактировать SQL уже применённых миграций.
6. Опция `--bootstrap` после миграций запускает DB bootstrap текущего приложения в новом процессе с `NODE_ENV=production`, без секретов окружения, только на собственной `restored.db`. Проверяются все строки/колонки, полный schema SQL и FK до/после; любое дополнительное изменение закрывает выпуск до отдельного разбора. Integration-test проверяет такой отказ на старой схеме. Локальная репетиция прошла с `bootstrap.unchanged=true`; это ещё не проверка целевой production-копии.
7. Собрать зафиксированный commit в отдельном checkout/build-каталоге; `DATABASE_PATH` указывает только на тестовую копию. Выполнить unit/API, браузерную приёмку, проверки файлов/авторизации/flags и CSS/JS. `outputFileTracingRoot` не менять: в проекте уже была регрессия раздачи статики под PM2.
8. Согласовать результаты и точный артефакт выпуска с владельцем. Порядок для подтверждённого адреса ниже; параметры PM2/storage/migrations остаются контрольными условиями, пока нет фактического inventory. Эта инструкция не разрешает выполнять переключение.

## Будущее переключение (после разрешения)

Окно остановки записи должно блокировать **все** писатели. `MAINTENANCE_MODE` сам по себе не гарантирует это: middleware пропускает авторизованные `/api/`, отдельные upload routes исключены; cron и webhooks живут отдельно. На время миграции требуется остановка процесса и фоновых задач/очередь повторной доставки webhook по согласованной процедуре. Нельзя молча терять оплату, пришедшую в это окно.

Создать свежую backup API + файловый snapshot и повторно проверить восстановление. Верифицированные аддитивные миграции применяет отдельная утверждённая процедура; текущий локальный CLI намеренно запрещён при `NODE_ENV=production`. Не обходить защиту сменой переменной окружения.

Предпочтительно сохранить действующий cwd и storage-path до отдельной миграции структуры deployment. При будущих versioned release directories каталоги `data`, `public/uploads` и nginx internal alias должны указывать на одно постоянное хранилище. Одного `DATABASE_PATH` недостаточно: файлы сейчас зависят от cwd.

Подготовить новую сборку до остановки текущей. Добавить её hashed assets в существующее накопительное хранилище без удаления старых. Переключить только утверждённый экземпляр `blabla`; не использовать `pkill -f next-server`, `fuser -k` или `git pull main` как выбор версии. Изменение nginx, если необходимо, — отдельный review diff, `nginx -t` и управляемый reload.

До снятия ограничений проверить HTTP/DOM: вход и сессии, библиотека, PDF/EPUB/TXT, чтение существующей личной пометки её владельцем, закрытие той же пометки для другого пользователя, source quote, uploads/Range, старый/новый CSS chunk, недоступность выключенных разделов, admin. Биллинг проверять по конфигурации/существующим записям без инициирования платежей. Сравнить counts, исходные row hashes, FK, files и flags с остановленной базой. Затем вернуть запись и проверить новые пометки/комментарии в контролируемом тестовом аккаунте.

## Откат

Сначала остановить переключение и сохранить логи/новую БД. Аддитивную схему обычно оставляют; возврат к прежнему коду разрешён только после проверки его работы с расширенной схемой и новыми блоками содержимого на копии. Нельзя считать старый рендерер совместимым с новым типом блока автоматически.

**Не восстанавливать старый backup поверх новых пользовательских записей.** Если код несовместим и требуется восстановление данных, вновь остановить все писатели, сохранить обе базы и файлы, составить отдельный план переноса новых записей/платежных событий с проверкой идемпотентности. Это отдельное решение владельца. Старые assets и предыдущий build сохраняются до завершения наблюдения.

## Первоначальный план для VPS (история; актуальные команды в начале документа)

Это последовательность **будущего согласованного выпуска**, а не выполненные действия. Последующее задание перенесло все серверные команды владельцу в Termius; агент к VPS не подключается. Для временной среды preflight уже получен; после финальной проверки Linux-пакета продолжать с этапа 3 в `test-environment.md`, небольшими блоками с контрольными точками.

1. **Read-only inventory владельцем перед будущим выпуском.** После подготовки отдельного тестового каталога скрипт можно запустить от root в Termius, сохраняя отчёт вне production:

   ```bash
   umask 077
   cd /srv/blabla-test/app
   node scripts/inspect-production.cjs /var/www/blabla \
     > /srv/blabla-test/reports/production-inventory.json
   ```

   Он выводит пути/права, Node/SQLite, counts/колонки/ledger, агрегат ролей, наличие прежних тестовых аккаунтов, modes flags без идентификаторов тестировщиков, имена env-переменных без значений. PM2 CLI не вызывается (даже status может запустить daemon): читается сохранённый `dump.pm2`, а процесс/окружение сверяются через `/proc`. Если сверка недоступна, отчёт помечает настройки как сохранённые, не подтверждённые runtime. Для nginx/TLS берутся только разрешённые директивы/метаданные сертификата, не содержимое ключей. `problems` означает неполноту; недоступность nginx/cron не означает отсутствие настройки. Других писателей, root-cron/systemd и повторную доставку webhook владелец подтверждает отдельно. `releaseReady=false` намеренно: inventory не даёт разрешения на выпуск.

2. **Зафиксировать состав релиза.** Текущее рабочее дерево содержит результаты нескольких итераций, включая ещё неотслеживаемые исходники и тесты. Review всех изменений → отдельный проверенный commit владельцем → точный SHA как идентификатор. Не использовать `git pull main` для выбора версии и не ограничиваться `git diff`: он не включает новые файлы. Проверить `git diff --check`, tracked ignored, секреты и отсутствие БД/uploads/env в артефакте. Push в этой сессии не выполняется.

3. **Снять свежий согласованный snapshot.** Сначала определить всех писателей и согласовать остановку записи/восстанавливаемую очередь webhook. После разрешения владельца остановить только подтверждённый PM2-процесс и связанные задачи; `MAINTENANCE_MODE` недостаточен. Использовать существующий `scripts/backup-sqlite.cjs` с фактическим абсолютным DATABASE_PATH и закрытым backup-каталогом вне релиза. Одновременно сохранить `public/uploads`, `data/community-uploads`, `data/music-uploads`, env и maintenance-конфигурацию (секреты — отдельная защищённая копия). Зафиксировать владельцев/права, counts, ledger, SHA файлов. Проверить восстановление БД и наличие каждого файла; возобновить старую версию, если репетиция выполняется заранее. Перед финальным переключением нужен свежий snapshot при новой остановке записи.

4. **Репетиция на восстановленной production-копии.** В закрытой offline-среде выполнить `release.sh --check … --bootstrap`. Отсутствующий ledger при уже существующих колонках, неизвестные миграции, несовпадающие checksums, потерянные файлы, изменения старых строк или runtime-DDL — остановка. Не применять `db:push`, не подавлять ошибки и не «чинить» ledger вручную. Исторические FK-проблемы должны совпасть и быть отдельно приняты владельцем. Реальные ключи оплаты/SMTP в среду тестов не передавать.

5. **Отдельный каталог кода, постоянное хранилище.** Если inventory подтвердит текущие пути, подготовить `/var/www/blabla/releases/<проверенный-SHA>`; прежний `/var/www/blabla` пока остаётся предыдущей версией и корнем существующих данных. Новый каталог содержит только код/собственные зависимости/сборку. Для runtime его `data` указывает симлинком на `/var/www/blabla/data`, `public/uploads` — на `/var/www/blabla/public/uploads`. Это сохраняет nginx internal alias и все существующие пути файлов без перемещения данных. Environment подключается из подтверждённого защищённого места. При иной фактической структуре сначала исправить этот план. Каталог `releases` не должен войти в Git или рекурсивную копию самого приложения.

6. **Собрать вне production VPS до остановки приложения.** При подтверждённых 1,9 GiB RAM использовать отдельный совместимый Linux amd64 builder: `npm ci` и `npm run build`, `DATABASE_PATH` только на восстановленную тестовую копию. Production-env и storage-симлинки подключать для runtime после переноса проверенного артефакта. Не переносить macOS node_modules на Linux VPS: native better-sqlite3 устанавливается и проверяется на целевой платформе. До подключения реальных данных выполнить unit/API, tsc, lint и smoke на закрытом тестовом порту. Для nginx-статики добавить содержимое нового `.next/static/` в существующий `/var/www/blabla/static-assets/` без `--delete`; сохранить старые hashed chunks. В этом варианте менять nginx/SSL не требуется, если inventory подтвердит alias.

7. **Отдельно разрешённое переключение.** Остановить запись, снять финальный snapshot, сравнить ledger/schema со свежей репетицией. Только после review применить нужные миграции существующим `migrate` из `lib/db/migrations.ts` через согласованный production-runner; текущий локальный CLI намеренно запрещает production, обходить его защиту сменой NODE_ENV нельзя. Точный production вызов не утверждён без целевой схемы. Если ledger уже полный, миграции не нужны. Переключить только `blabla` на `releases/<SHA>/ecosystem.config.cjs` (cwd теперь вычисляется из расположения config), проверить фактический cwd/DB/env и сохранить прежний PM2 config. Не запускать оба экземпляра с реальной SQLite одновременно. Команду PM2 выбирать по подтверждённому текущему процессу; массовые `pkill`/`fuser` исключены.

8. **Приёмка до возврата записи.** Проверить вход/admin, старые пользовательские книги PDF/EPUB/TXT, точный anchor, свои/чужие приватные пометки, комментарии, файлы/Range, старые и новые CSS/JS, медиатеку и отключённые разделы. Сравнить исходные строки/counts/ledger/FK/files/настройки с финальным snapshot. Согласованный стартовый профиль незавершённых функций: `rooms`, `room_creation`, `host_programs`, `paid_events`, `experimental` — `off` либо ограниченный доступ по выбору владельца; менять только эти modes, не testerIds/платёжные ключи/тарифы. Существующие билеты не отключать вместе с программами ведущих. Проверить прямые URLs/API. Затем вернуть запись, проверить создание пометки и комментария в контролируемом аккаунте, восстановить все cron/webhook writers и наблюдать ошибки. `pm2 save` — после успешной проверки.

Откат: сохранить новую БД/files, вернуть только проверенный совместимый предыдущий код и PM2 cwd, оставить расширенную схему и накопленные assets. При несовместимости остановить запись и согласовать перенос новых данных; старую БД поверх новых записей не восстанавливать.
